บทที่ 1 · พื้นฐาน

Probability = สิ่งที่สนใจ / ทั้งหมดที่เป็นไปได้

นิยาม + ตัวอย่าง
P(event) = จำนวนแบบที่สนใจ
           ─────────────────
           จำนวนแบบทั้งหมด

/* ทอยลูกเต๋า 1 ลูก */
P(ได้ 6)     = 1/6
P(ได้เลขคู่)  = 3/6 = 1/2
P(ได้ ≤ 4)   = 4/6 = 2/3

/* ค่าเสมออยู่ระหว่าง 0 ถึง 1
   P = 0 → เป็นไปไม่ได้
   P = 1 → แน่นอน 100% */
ในโลก CS
/* hash function กระจาย uniform
   ใส่ key ลง table ขนาด m ช่อง */
P(ลงช่องที่ 0) = 1/m

/* Quick Sort random pivot
   จาก n ตัว */
P(ได้ pivot แย่สุด) = 1/n
P(ได้ pivot ใน 50% กลาง) = 1/2
  ← เหตุผลที่ average O(n log n)!

/* สุ่ม bit 32 ตัว */
P(ได้ค่าเจาะจงค่าหนึ่ง) = 1/2³²
  ≈ 1 ใน 4 พันล้าน
Probability คือเครื่องมือวิเคราะห์ "โค้ดที่มีการสุ่ม" และ "input ที่ไม่รู้ล่วงหน้า" — สองอย่างที่เจอทุกวัน
บทที่ 1 · กฎ

กฎบวก (OR) และ กฎคูณ (AND)

กฎบวก — "อย่างใดอย่างหนึ่ง"
/* events ไม่ทับกัน (mutually exclusive) */
P(A หรือ B) = P(A) + P(B)

ทอยเต๋า: P(1 หรือ 6) = 1/6 + 1/6 = 1/3

/* ถ้าทับกันได้ ต้องลบส่วนซ้ำ: */
P(A หรือ B) = P(A) + P(B) − P(A และ B)

P(คู่ หรือ ≥4)
= 3/6 + 3/6 − 2/6   /* {4,6} ซ้ำ */
= 4/6 = 2/3
กฎคูณ — "ทั้งคู่เกิด" (independent)
P(A และ B) = P(A) × P(B)

/* ทอยเต๋า 2 ลูก ได้ 6 ทั้งคู่ */
P = 1/6 × 1/6 = 1/36

/* ใน CS: server 2 ตัว
   แต่ละตัว down ด้วย P = 0.01 */
P(down พร้อมกัน) = 0.01 × 0.01
                 = 0.0001
/* → redundancy ลดความเสี่ยง
   จาก 1% เหลือ 0.01%! */
Trick ที่ใช้บ่อยสุด: P(อย่างน้อย 1 ครั้ง) = 1 − P(ไม่เกิดเลยสักครั้ง) — คำนวณฝั่งตรงข้ามง่ายกว่าเสมอ
บทที่ 1 · Trick

Trick: คิดจากฝั่งตรงข้าม (Complement)

"อย่างน้อยหนึ่งครั้ง" นับตรงๆ ยาก — นับ "ไม่เกิดเลย" แล้วเอา 1 ลบ ง่ายกว่ามาก

ตัวอย่าง: ทอยเต๋า 4 ครั้ง
P(ได้ 6 อย่างน้อย 1 ครั้ง) = ?

/* ทางยาก: นับกรณีได้ 6
   1 ครั้ง, 2 ครั้ง, 3, 4 ครั้ง... */

/* ทางง่าย: */
P(ไม่ได้ 6 เลย) = (5/6)⁴ ≈ 0.482

P(ได้อย่างน้อย 1) = 1 − 0.482
                  = 0.518
ใน CS: retry logic
/* API สำเร็จ 90% ต่อครั้ง
   retry สูงสุด 3 ครั้ง
   P(สำเร็จอย่างน้อย 1 ใน 3)? */

P(fail ทั้ง 3) = 0.1³ = 0.001

P(สำเร็จ) = 1 − 0.001 = 0.999

/* retry 3 ครั้ง เปลี่ยน
   ความสำเร็จ 90% → 99.9%!
   นี่คือเหตุผลที่ระบบจริง
   มี retry เสมอ */
สูตรจำ: P(at least one) = 1 − (1−p)ⁿ — ใช้กับ retry, hash collision, packet loss
บทที่ 1 · Expected Value

Expected Value — ค่าเฉลี่ยระยะยาว

E[X] = Σ (ค่า × ความน่าจะเป็น) — ถ้าทำซ้ำหลายๆ ครั้ง ผลเฉลี่ยจะเข้าใกล้ค่านี้

ตัวอย่าง
/* ทอยเต๋า 1 ลูก ค่าคาดหวัง? */
E[X] = 1·(1/6) + 2·(1/6) + ... + 6·(1/6)
     = 21/6 = 3.5

/* เกมพนัน: จ่าย 10 บาท
   ถ้าทอยได้ 6 รับ 50 บาท */
E[กำไร] = (1/6)(+40) + (5/6)(−10)
        = 6.67 − 8.33
        = −1.67 บาท/ตา
/* เล่นนานๆ เจ๊งแน่นอน! */
ใน CS: Average Case Analysis
/* Linear Search หา x ใน n ตัว
   (x อยู่ในแน่ๆ สุ่มตำแหน่ง uniform) */

E[จำนวนเปรียบเทียบ]
= 1·(1/n) + 2·(1/n) + ... + n·(1/n)
= (1+2+...+n)/n
= (n+1)/2
≈ n/2  → O(n)

/* นี่คือที่มาของคำว่า
   "average case = n/2"
   ที่เรียนใน Big O! */
คำว่า "average case O(...)" ทุกครั้งที่เห็น มาจาก Expected Value ทั้งนั้น — Quick Sort average O(n log n) ก็พิสูจน์ด้วย E[X]
บทที่ 1 · Hashing

Probability ใน Hash Table

Collision Probability
/* table m ช่อง ใส่ key ที่ 2
   (มี key เดิม 1 ตัวแล้ว) */
P(collision) = 1/m

/* ใส่ n keys ลง m ช่อง
   Expected keys ต่อช่อง = n/m
   เรียกว่า Load Factor (α) */

α = n/m
α = 0.5  → เฉลี่ยครึ่งช่องว่าง เร็ว
α = 1.0  → เริ่มชนบ่อย
α > 1.0  → chain ยาว ช้าลง

/* Expected chain length = α
   → lookup average O(1 + α) */
ทำไม Hash Table O(1)?
/* คำตอบ: O(1) "average"
   ไม่ใช่ O(1) worst!

   Worst case: ทุก key ชนช่องเดียว
   → chain ยาว n → O(n)

   แต่ P(เกิด worst) น้อยมาก
   ถ้า hash function ดี + α ต่ำ

   → นี่คือ probabilistic
     guarantee ไม่ใช่ absolute */

/* กฎปฏิบัติ: resize เมื่อ α > 0.75
   (Java HashMap ใช้ค่านี้) */
Hash Table เร็วเพราะสถิติ — ความเข้าใจ probability คือความเข้าใจว่าทำไม data structure นี้ถึงทำงานได้
บทที่ 1 · Birthday Paradox

Birthday Paradox — collision มาเร็วกว่าที่คิด

แค่ 23 คน โอกาสมีวันเกิดตรงกัน > 50% — สวนสัญชาตญาณ แต่สำคัญมากกับ hashing

คำนวณ
/* คิดจากฝั่งตรงข้าม:
   P(ไม่มีใครตรงกันเลย) */

คน 2: P = 364/365
คน 3: P = 364/365 × 363/365
...
คน 23:
P(ไม่ตรงเลย) ≈ 0.493
P(มีคู่ตรง) ≈ 0.507  ← เกิน 50%!

/* n คน, d วัน:
   P(collision) ≈ 1 − e^(−n²/2d)
   collision เกิดเมื่อ n ≈ √d */
ผลต่อ Hashing จริง
/* hash 32-bit: 2³² ≈ 4.3B ค่า
   คิดว่าปลอดภัย? */

collision คาดว่าเกิดที่
n ≈ √(2³²) = 2¹⁶ = 65,536 keys!

/* แค่ 65K keys ก็เริ่มชนแล้ว
   ไม่ใช่ 4 พันล้าน! */

/* นี่คือเหตุผลที่:
   - git ใช้ SHA-1 160-bit (ตอนนี้ SHA-256)
   - UUID ใช้ 128-bit
   - อย่าใช้ hash 32-bit
     กับข้อมูลเยอะๆ */
กฎ √d: hash space ขนาด d จะเริ่มชนที่ประมาณ √d keys — จำไว้ตอนเลือกขนาด hash
บทที่ 1 · โค้ด C

การสุ่มใน C — rand() ใช้ให้ถูก

#include <stdio.h>
#include <stdlib.h>
#include <time.h>

int main() {
    srand(time(NULL));            /* seed ครั้งเดียว! ไม่งั้นได้เลขเดิมทุกรอบ */

    int d6   = rand() % 6 + 1;              /* 1..6 ทอยเต๋า */
    int pct  = rand() % 100;                /* 0..99 */
    double p = (double)rand() / RAND_MAX;  /* 0.0..1.0 */

    /* เหตุการณ์ความน่าจะเป็น 30% */
    if (p < 0.3) printf("เกิด! (P=0.3)\n");

    /* จำลองทอยเต๋า 60,000 ครั้ง — Law of Large Numbers */
    int count6 = 0;
    for (int i = 0; i < 60000; i++)
        if (rand() % 6 == 5) count6++;
    printf("ได้ 6: %d ครั้ง (คาด ~10000)\n", count6);
    /* รันจริงได้ ~9,950-10,050 — เข้าใกล้ E[X] เสมอ */
}
Law of Large Numbers: ทำซ้ำมากพอ ค่าเฉลี่ยจริงจะลู่เข้า Expected Value — ฐานของ simulation ทุกชนิด
บทที่ 1 · Simulation

Monte Carlo — ประมาณค่า π ด้วยการสุ่ม

ปาเป้าสุ่มลงสี่เหลี่ยม แล้วนับสัดส่วนที่ตกในวงกลม — ได้ π โดยไม่ต้องรู้สูตรอะไรเลย

/* วงกลมรัศมี 1 ในสี่เหลี่ยม 2×2
   พื้นที่วงกลม/สี่เหลี่ยม = π/4
   → สุ่มจุด แล้วนับสัดส่วน = ประมาณ π/4 */

double estimate_pi(int trials) {
    int inside = 0;
    for (int i = 0; i < trials; i++) {
        double x = (double)rand() / RAND_MAX * 2 - 1;  /* -1..1 */
        double y = (double)rand() / RAND_MAX * 2 - 1;
        if (x*x + y*y <= 1.0) inside++;      /* ในวงกลม? */
    }
    return 4.0 * inside / trials;
}

/* trials = 1,000      → π ≈ 3.16   (หยาบ)
   trials = 1,000,000  → π ≈ 3.1421 (ใกล้แล้ว)
   ยิ่งสุ่มเยอะ ยิ่งแม่น — Law of Large Numbers อีกแล้ว! */
Monte Carlo ใช้จริงใน: การเงิน (ประเมินความเสี่ยง), เกม AI (MCTS ใน AlphaGo), physics simulation, ray tracing

บทที่ 1 · MCQ

API สำเร็จ 80% ต่อครั้ง — retry 2 ครั้ง (รวมยิง 3 ครั้ง) P(สำเร็จ)?

คิดจากฝั่งตรงข้าม:
P(fail 1 ครั้ง) = 0.2
P(fail ติดกัน 3 ครั้ง) = 0.2 × 0.2 × 0.2 = 0.008
P(สำเร็จอย่างน้อย 1 ครั้ง) = 1 − 0.008 = 0.992 = 99.2%

retry 2 ครั้ง เปลี่ยน 80% → 99.2%
